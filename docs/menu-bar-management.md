## RockshinOps implementation

`internal/menubar` implements independent Go settings and AppKit behavior. `menu_bar.go` exposes MyGo bindings and registers global shortcuts. `src/menu-bar-view.tsx` renders the bilingual configuration page. No HTTP IPC or JavaScript native sampling is introduced.

Native status-item boundaries hide icons to their left by expanding separator width. Command-drag events move actual status items; results are checked against observed sections. AppKit handles expansion, hover, delayed collapse, context menus, appearance overlays and display/Space changes. ScreenCaptureKit captures individual status-item windows; image data stays local. Native panel selections move only the chosen item to the left edge of the visible status items without simulating a click or activating its app. The layout’s explicit Open Menu action still clicks the resolved item. Both paths require Accessibility and return explicit errors for vanished or offscreen items. Gesture timing runs outside AppKit's queue.

Settings live in the existing user configuration directory as `menu-bar.json`; root `rockshinops.json` defines first-run defaults. Management is disabled by default. The macOS status bar owns ordering persistence; no private preference database is edited. Disabling management removes its boundary items and reveals hidden items. Existing metric sampling remains independent.

## Usage and boundaries

1. Quit Ice, open **Menu Bar Management**, and enable management.
2. Grant Accessibility for movement and activation, and Screen Recording for actual icon previews. Refresh/restart as macOS requests.
3. Select an icon and move it to a section, or drag it within the layout. RockshinOps’ own arrow and metric item are included. Command-drag is also available in the native menu bar; restart and re-enabling preserve the saved positions.
4. The solid arrow opens the overflow panel centered under its anchor, clamped to 12 pt inside the current screen’s visible edges. Selecting an icon reveals only that item; click it in the system menu bar to open its menu.
5. **General → Temporary icon duration** defaults to 15 seconds and accepts 5–60 seconds. An open menu/popover keeps the icon visible beyond that duration; afterward it returns to its original section and neighbor. The general panel-collapse delay is separate. Escape closes the overflow panel; the search shortcut searches native icon names and owners.

The layout uses pointer capture and a frame-synchronized drag preview. Neighboring icons make room before release; same-section and cross-section moves animate from their current visual position, including interrupted moves and failed-operation rollback. Only release sends a native move request. Escape or release outside a section cancels the preview. Pointer selection uses a translucent fill; keyboard focus remains visible. Reduced Motion skips spatial settling while keeping direct pointer tracking.

This is a macOS implementation. Windows/Linux retain ordinary monitoring and report management as unsupported. It uses ScreenCaptureKit screenshot APIs available on macOS 14 and newer. Native item clicks are delivered to actual status-item coordinates; app-specific menu/popover behavior still requires compatibility testing. Hidden items are resolved by window ID even when their windows are offscreen. Multi-display, notch/fullscreen/auto-hide and sleep/wake behavior still require acceptance; see the single current progress record in `STATUS.md`.

## Recovering Accessibility after a local update

If dragging is disabled while System Settings shows RockshinOps enabled, check the running app's **Accessibility** status. The app uses `AXIsProcessTrusted()` on every native state read; it does not infer authorization from a settings toggle or from screen-recording access.

For a stale grant, quit RockshinOps, remove its old entry in **System Settings → Privacy & Security → Accessibility**, add the installed `/Applications/RockshinOps.app`, enable it, then reopen the app. This changes a system permission and must be performed or explicitly authorized by the user. The in-app recovery button opens that settings pane even when macOS suppresses another authorization prompt. It neither grants access nor resets other apps' permissions. An unsuccessful settings launch is reported explicitly.

Local packages currently use MyGo's default ad-hoc signature. The installed package inspected on 2026-10-29 has a cdhash-only designated requirement; no valid code-signing identity was present on the build machine. Such a requirement identifies one exact build, so a replacement can invalidate an earlier grant even while its settings entry remains enabled. A stable Developer ID Application signing identity configured through `macos.signingIdentity` is needed for distributed builds to maintain a compatible signing identity across updates. The updater archive signature is separate and does not provide macOS app identity. Do not weaken the designated requirement or rewrite the privacy database to bypass reauthorization. See Apple's [TN3127: Inside Code Signing — Requirements](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements).

The reported installed build reproduced the mismatch: one running `/Applications/RockshinOps.app`, Accessibility enabled in System Settings, denied in the app, and drag controls disabled; Screen Recording remained granted. The isolated native action test in `work/menu-permission-recovery/` failed before and passed after adding the direct recovery route, including a failed-settings-launch case. This test checks the recovery action, not whether the OS has accepted a new user grant. After explicit user authorization and user-completed macOS authentication, the old entry was removed, `/Applications/RockshinOps.app` was re-added and the app restarted. The app then reported Accessibility granted, and the user confirmed manual dragging works normally. This restored the existing installed binary; the newly built recovery-guidance package was not installed. Existing real permission checks remain unchanged.
